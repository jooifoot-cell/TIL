### 理解したこと

#### GitHub Actionsは「自動実行する場所」

GitHubはコードや設定を保存・管理する場所で、GitHub Actionsは決められたタイミングや操作をきっかけに処理を実行する環境として使える。

現在作っているブログ自動化では、GitHub ActionsがNode.jsの処理を実行し、GSCやWordPressなどの外部サービスと通信する役割を持つ。

#### REST APIとXML-RPCはWordPressにアクセスする別々の入口

通常の記事取得・作成・更新にはWordPress REST APIを利用する。

一方、Cocoon固有のSEOカスタムフィールドについてはXML-RPCを利用する。

同じWordPressを操作していても、目的によってアクセス方法を使い分けられることを理解した。

#### `article.json` はAIと実行処理の境界

AIがWordPressを直接操作するのではなく、AI側で記事内容や操作内容を `article.json` にまとめる。

そのJSONを受け取ったNode.js側が、安全性を確認した上でWordPressへの反映を行う。

```text
ChatGPT
  ↓
article.json
  ↓
Node.js / GitHub Actions
  ↓
WordPress
```

これにより、AIの判断部分と実際の書き込み処理を分離できる。

#### `content-index.json` はGSCとWordPressを結ぶ住所録

GSCには検索結果に表示されたURLが記録されているが、そのURLだけではWordPressのどの投稿を更新すべきか安全に判断できない。

そこでWordPressの投稿ID・URL・タイトルなどをまとめた `content-index.json` を作り、URLを正規化して対応させる。

```text
GSCのURL
  ↓
URL正規化
  ↓
content-index.json
  ↓
WordPress投稿ID
```

タイトルやslugから推測して記事を更新するのではなく、投稿IDまで特定してから処理することで誤更新を防げる。

#### GSCの取得では「取れたデータ」だけでなく「全部取れたか」が重要

GSC APIでは一度に取得できる件数に上限があるため、`startRow` を使ってページングする必要がある。

また、途中のページ取得に失敗した状態で保存すると「取得できたように見える不完全なデータ」が残るため、全ページの取得に成功した場合だけ保存する。

`fetch-history.json` に取得件数・ページ数・complete状態を残すことで、データ取得そのものが正常だったか確認できる。

#### AIと通常プログラムは得意な仕事を分ける

現在の構成では、判断が必要な部分をChatGPT、決められた処理を正確に繰り返す部分をNode.js / GitHub Actionsに担当させる。

将来的には次のような流れを目指す。

```text
GSC
 ↓
Node.jsで集計・候補抽出
 ↓
ai-handoff.json
 ↓
ChatGPTが改善内容を判断
 ↓
article.json
 ↓
Node.js / GitHub Actions
 ↓
WordPress
```

AIに大量の生データをそのまま渡すのではなく、通常プログラム側で必要な情報まで絞ってからAIに渡すことで、処理を安定させながらトークン消費も抑えられる。
